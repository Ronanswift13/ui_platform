# 06 Refactor Policy

## 1. 重构触发条件

以下情况应触发重构：
- 单个页面文件超过 400 行
- 同一段 HTML/JS 在 3 个以上位置重复
- 页面加载时间超过 3 秒
- 组件职责混乱（同时包含数据请求、状态管理和展示逻辑）
- CSS 选择器嵌套超过 3 层
- 新增功能需要修改超过 3 个不相关文件

## 2. 重构模式清单

### 2.1 页面拆分
**触发**：页面文件超过 400 行
**做法**：
- 提取可复用区域为 `components/` 下的独立模板
- 使用 Jinja2 `{% include %}` 引入
- 组件内不得有 `fetch` 调用

### 2.2 脚本模块化
**触发**：JS 逻辑超过 300 行或存在全局变量污染
**做法**：
- 使用模块化对象模式（如 `const Module = { init(), destroy(), ... }`）
- 状态集中到单一 State 对象
- 定时器 ID 统一注册，页面卸载时清理

### 2.3 样式变量化
**触发**：同一颜色值出现 3 次以上
**做法**：
- 提取为 CSS 变量
- 变量定义在 `:root` 中
- 命名使用 `--{prefix}-{category}-{name}` 格式

### 2.4 布局升级
**触发**：使用浮动、绝对定位或大量 margin hack 实现布局
**做法**：
- 改用 CSS Grid（页面级）或 Flexbox（组件级）
- 使用 `grid-template-areas` 命名区域
- 响应式通过 `@media` 改变 grid-template

## 3. 重构禁止事项
- 禁止一次性重构全部页面
- 禁止重构期间新增功能
- 禁止删除已有路由
- 禁止改变后端 API 接口
- 禁止引入新的框架级依赖

## 4. 重构后必须输出

每次 UI 改造后必须输出 root cause 复盘：

```markdown
### Root Cause 复盘

**核心问题**：（本次修改解决的核心可维护性问题）
**原因分析**：（为什么原页面/组件难维护）
**采用模式**：（本次采用的重构模式，参考 2.x 清单）
**禁止反模式**：（哪些反模式以后禁止再出现）
**沉淀规则**：（哪些规则应该写入 04_quality_audit.md）
```

复盘内容写入两个文件：
- `04_quality_audit.md` — 写入通用质量规则
- `07_learning_log.md` — 写入本项目经验记录
